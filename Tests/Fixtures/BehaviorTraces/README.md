# Deterministic Mock behavior traces

Generated by `BehaviorTraceTests` from real `SurfaceSession`/engine/Mock operations and an output-recording fake device. No CoreMIDI or actual device is opened. Regenerate explicitly with `BCR_RECORD_BEHAVIOR_TRACES=1 swift test --build-path build/swiftpm --filter BehaviorTraceTests`; ordinary runs compare every JSON byte. Keys are sorted; Foundation encodes finite numbers; UTF-8 ends with one LF. These fixtures are unrelated to the four frozen shared simulation protocol fixtures.

Each step contains:

- `input`: operation and semantic payload, all raw input MIDI byte arrays received that step, source, group context, injected reference-date seconds. An empty messages array means a software/context operation. The unmapped-input fixture starts on a connected fake hardware route; no learned binding exists for its channel-15 input. Group context comes from the Mock setup; real BCR group keys do not report themselves.
- `result`: accepted, optional reason, changed authoritative parameter values, action callback count for that step. Raw input acceptance is measured by the session's accepted-input observer, independently from feedback. A software operation may succeed without changing a value.
- `output`: ordered `sent` byte arrays confirmed by the transport returning successfully; `suppressed` carries generated byte arrays and observe-policy reason; `rejected` contains disconnected/failed transport messages and reason; `deferred` is empty because these traces use immediate feedback. These are messages to the modeled controller, never real hardware.
- `observation`: for currently assigned controls, `last_input` records the last input the engine accepted and `last_generated_feedback` is the engine's generated output, including suppressed/disconnected attempts. It must not be treated as successfully sent or physically observed. The explicit output sequence carries successful-send evidence. `connection_generation` is the fake route generation; `binding_revision` is the session mapping revision. `connected` is route status, not write permission.

`last_input`/`last_generated_feedback` are `null` when that control has no such record. `result.reason` is `null` for accepted operations. `confirmed_device_display` is always `null`: this model has no independent device display readback or arrival acknowledgement. Nothing infers a physical position or display from a successful send. Null information remains unknown; no product fields were added to fill the trace.

## Neutral declarations (L round)

These declarations come only from this host's `HardwareMap`, `BCRControlID` and assignment mode in test support. No public product API is added. Every original field, array shape and value remains present.

- Each `input` adds `element`, `role` and `context`. Stable physical IDs are `encoder.top.N` for the same top rotary/push across all four groups, `encoder.rowR.N`, `button.rowR.N` and `button.user.N`. A relative encoder declares `rotation`; an absolute encoder declares `position`; button edges declare `press`. Push and rotary share the physical element but have different roles. Software/context operations have no physical input and declare null element/role; the unmapped input also declares both null because its physical role is unknown.
- Context is exactly `{ "kind": "group", "value": 1...4 or null }`. A mapped top address declares its group. Mock context is known from the Mock's active group. Hardware-source operations involving other controls declare null: the hardware group buttons do not report group state. The old `hardware_context` remains the raw Mock setup context; the new declaration does not present it as a physical observation.
- `output.declarations` is an ordered array. Each entry's `source_field` is an absolute JSON pointer to one original `/output/sent/N`, `/output/suppressed/N` or `/output/rejected/N` entry. This preserves the original bare byte arrays and reason objects. Every actual output gets `category`, `target`, `affected`; this trace set contains only mapped `display` effects. Targets are the physical element plus `.ring` for continuous controls or `.light` for buttons. `affected` contains that physical element. No side effects are declared because this set contains no movement or management command. Empty deferred output needs no entry.
- `observation.declarations` similarly points to each original `last_input`, `last_generated_feedback` and `confirmed_device_display`. An absent input is `unknown`; a retained accepted input is `observed` (historical input, not a device display acknowledgement). Missing generated feedback is `unknown`. Non-null generated feedback has `state: null`: the engine's generation record cannot distinguish merely generated, suppressed, failed and successfully sent output. The transport output remains independent evidence; the declaration never relabels generation as arrival. Confirmed display remains unknown with no physical element because there is no readback.
- No per-observation hardware freshness is invented; neither real-device timing nor hardware group switching has been verified. Declaration nulls mean missing source knowledge, not a contract failure.
