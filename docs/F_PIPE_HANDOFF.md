## Flow commands and feedback

Recommended **control IDs**, independent of business parameter IDs:

| Pipe intent | Stable control ID → default parameter ID | Reason | Default hardware qualification/binding |
| --- | --- | --- | --- |
| prepare | `pushEncoder.1.1` → `general.1` | existing learned absolute CC8; same group, distinct endpoint | learned absolute input + neutral parameter binding present; not an attended-qualified flow command |
| start | `pushEncoder.1.2` → `general.2` | existing learned absolute CC9; adjacent independent axis | same |
| pause | `pushEncoder.1.3` → `general.3` | existing learned absolute CC10; avoids unqualified buttons | same |
| cancel | `pushEncoder.1.4` → `general.4` | existing learned absolute CC11; independent of the first three | same |

These are absolute knobs, not momentary buttons. Pipe must define a new-action threshold, return-to-rest
rule and fresh-generation preparation; continuous high values must never trigger repeats. The consumer
must inspect the exact learned map and require new hardware events. These IDs are recommendations, not
an automatic hardware authorization. The default hardware profile can report ignored/unmapped input;
merely being listed does not make a workflow runnable. Four button commands require a separately
qualified candidate and explicit bindings; the two-button teleoperation candidate is not a four-button flow map.

The neutral default already binds `pushEncoder.1.1..8` to `general.1..8` (see
`Sources/BCRSurfaceDomain/NeutralConfiguration.swift`). Their parameter range is **0..100**, while learned
control raw values are **0..127**. Use `general.1..4` as the stable default command parameter IDs; Pipe
supplies the business interpretation. No `flow.*` parameter is silently installed. Existing axis
bindings can produce accepted hardware input; the 52 visualization-only buttons remain ignored and
have no usable indicator feedback. Attended validation still has to confirm the selected knobs/current
preset, action thresholds and full flow. No default configuration, map or profile is changed this round.

All seven `general.*` definitions and assignments exist in the neutral default. They are domain-neutral;
Pipe selects the state/progress/link meaning and must pin the configuration and mapping. The existing
learned map supplies absolute value feedback; physical display of these exact rings and flow semantics
remain unqualified. Provider configuration owns the parameter→control association.
For control contract 1.4 the corresponding display request uses the **control ID**, e.g.
`surface_control_feedback {expected:<pinned>,control_id:"pushEncoder.1.6",kind:"value",value:64}`.
That call writes the display overlay only and does not write `general.6`. Match the configuration
association and the feedback event's control_id/expected/sequence to the authoritative Pipe state; a
Provider `console_events` feedback.sent payload identifies MIDI/control and does not manufacture a
business parameter relationship. `sent` proves transport acceptance, not a physical light.

The existing explicit simulation profile has `simulation.arm/start/pause/cancel/state/progress/link`.
Its command controls are `pushEncoder.1.1..4`, state/link use `button.1.1/1.2`, progress uses
`pushEncoder.1.5`. It remains a simulation fixture and is not the default hardware binding or qualification.
